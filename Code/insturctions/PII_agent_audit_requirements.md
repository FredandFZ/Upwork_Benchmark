# PII Clean 已发布项目的 Agent 审核要求

## 1. 审核目标

本审核用于检查已经发布到 `Datasets/PII_clean_project/<项目ID>/chat_messages.json`
的结果是否真正满足 PII Clean 要求。

审核的核心不是“两个文件有多少字不同”，而是同时回答四个问题：

1. 原始身份信息、私有资源和真实凭据是否已经安全移除；
2. 本来不该改的公共名称、技术术语和项目事实是否得到保留；
3. 消息的需求、决定、状态、条件和前后关系是否仍与原文相同；
4. 替换后的聊天是否自然、完整，并且在整个项目中保持一致。

Phase 6 已通过不等于本次审核可以省略。Phase 6 擅长检查确定性的残留、格式和一致性问题，
但无法完全排除上游没有识别出的 PII、语义相近但事实已变化的改写，以及阅读后才能发现的
轻微文本问题。

本审核默认是**只读审核**。Agent 先报告问题，不直接修改原始文件或已发布文件。

## 2. 审核输入与范围

每个项目至少读取以下三个文件：

```text
Datasets/project/<项目ID>/chat_messages.json
Datasets/PII_clean_project/<项目ID>/chat_messages.json
Datasets/PII_clean_project/_manifests/<项目ID>.json
```

其中：

- 第一个文件是审核依据，包含原始聊天，可能含有真实 PII；
- 第二个文件是待审核的已发布结果；
- manifest 用于确认项目版本、源文件指纹、输出指纹和 Agent 修复记录。

审核范围只包括 PII Clean 实际处理的 `chat_messages.json`。项目目录中的其他文件只是复制，
不应被误认为已经由该流程脱敏。

审核必须覆盖项目内的**全部消息**，不能用抽样结果宣称整个项目通过。可以分批审核并保存
进度，但最终结论必须建立在所有消息均已审核的基础上。

消息序号 `ordinal` 是数组中的 1-based 位置：第一条消息为 1，第二条为 2。原文件与发布
文件必须按这个位置逐条对齐，不按相似文本重新配对。

## 3. PII Clean 的总原则

### 3.1 必须替换或安全处理的内容

只要一个值单独出现或结合项目上下文后，能够识别真实个人、私有项目、私有组织、账号、
私有通信端点或私有技术资源，就属于隐私敏感内容。

以下内容必须替换为自然、虚构且不可操作的值，或按照凭据规则安全处理：

- 真实人名，以及被当作人名使用的姓名片段；
- 个人邮箱、电话号码、用户名和社交账号；
- 私有项目、产品、品牌、公司、团队和内部简称；
- 私有域名、仓库、路径、仪表盘、文档、邀请、订阅、Webhook 和会议链接；
- 私有 URL 路径或查询参数里的资源标识，即使公共网站域名本身可以保留；
- 具体地址、与参与者绑定的地点；
- 雇主、学校、家庭成员等能够缩小身份范围的个人经历；
- 账号编号、客户编号、租户编号、钱包地址等账号或链上标识；
- 密码、API Key、Access Token、私钥、助记词、Webhook Secret 等真实凭据。

凭据的最终文本必须是本地程序生成的、确定无效的假凭据。不得保留真实值，也不得残留
`<SECRET_CANDIDATE:...>`、`[PERSON_001]` 等内部标记或旧式占位符。

### 3.2 必须保留的内容

以下内容通常不是 PII，而且往往是项目需求的一部分，不能为了“脱敏”随意替换：

- 公共公司和公共服务，例如 GitHub、Stripe、AWS、Google、Zoom；
- 公共技术、协议、标准、网络、代币和框架，例如 OAuth、USDC、ERC-721、AES-256、
  PostgreSQL、React Native；
- 文件格式、函数名、事件名、环境名和其他明确承载需求的技术标识；
- 普通动词、常用名词和不具有识别性的通用短语；
- 有序列表的编号，如 `1.`、`2.`、`3.`。

判断标准是“公共还是私有、是否能够识别对象”，而不是“看起来像不像专有名词”。例如，
完整的私有名称 `Project Rebuild` 应被替换，但普通动词 `rebuild` 本身不应因此被替换。

公共平台和平台上的私有资源要分开判断。例如 `GitHub` 可以保留，但某个私有仓库的组织名、
仓库名和路径必须替换；`Google Meet` 作为产品名可以保留，但可直接加入真实房间的链接不能保留。

### 3.3 允许发生的变化

以下变化本身不是错误：

- 私有实体被换成自然的虚构实体；
- 真实邮箱、链接、域名、账号和地址被换成虚构值；
- 真实凭据被换成明显无效的假凭据；
- 金额、数量、百分比、日期、期限、版本、文件名等业务参数按转换方案变为新值；
- 消息被重新措辞；长消息改变句式、语序或分句方式。

审核业务参数时，不能要求输出保留原数值。应检查的是：新值仍代表同一个业务参数，单位、
对象、条件和作用没有改变；跨消息的修改历史与原文对应；原文明确给出的计算关系仍成立。

裸数字只能按它在原消息中的具体位置和含义判断。例如一条消息中有获奖人数、日期和百分比时，
不能因为其中一个 `5` 需要变化，就要求所有字符 `5` 一起变化。

### 3.4 绝对不允许发生的变化

转换方案只允许改变身份值、凭据和指定业务参数，不允许重新设计项目事实。下列任一变化都
属于错误：

- 请求变成陈述，拒绝变成同意，问题变成已经确定的结论；
- 肯定、否定、可能、必须、条件成立后才执行等语气发生变化；
- 批准、拒绝、延期、取消、确认或变更决定丢失、变弱或被凭空添加；
- 未开始、进行中、已交付、已验证、阻塞、失败或放弃等执行状态改变；
- 原本未确定的问题被擅自补成确定答案，或明确结论变得含糊；
- 行为的执行者、操作、对象、范围、前提、结果发生变化；
- 因果方向、时间先后、`if X then Y` 的条件关系发生变化；
- production/staging、mainnet/testnet、自动/手动、链上/链下、无限/封顶、即时/延迟等事实互换；
- 触发机制、重置或过期规则、访问权限、认证要求发生变化；
- 原文中的需求、限制、决定或交付结果被总结掉；
- 输出增加原文没有承诺、解释、原因、时间、步骤或功能；
- 一个公共工具、协议或标准被换成另一个看似合理但不同的工具、协议或标准。

## 4. 每条消息的审核步骤

对 ordinal `N`，按以下顺序审核原文件第 `N` 条和发布文件第 `N` 条。

### 4.1 结构与字段

- 两个文件消息总数必须相同，不能缺失、重复或调换消息；
- 发布行必须保留对应的 `message_user_type`，且值与原行完全一致；
- 发布行中的 `message` 必须是字符串；
- `sender_id` 和 `created_ts` 必须从发布行删除；
- 除上述预期变化外，不得无故新增、删除或改变其他字段。

### 4.2 隐私与凭据

- 先识别原消息中的所有 PII，而不是只查已知名单；
- 检查原始值、简称、别名、大小写变化、带空格或标点的变体是否仍出现在输出中；
- 检查输出中的新邮箱、URL、账号、电话和凭据是否为安全的虚构值；
- 合成邮箱和 URL 应使用保留的不可解析域名，例如 `.example`，不能生成看似真实、可能可用的地址；
- 可操作的会议链接不能继续使用真实公共会议主机；
- 检查原始 `sender_id` 是否被复制进消息正文；
- 检查替换值是否意外包含原值，避免只在原名称外面加前后缀的伪脱敏；
- 检查普通词是否被错误当成 PII 替换。

### 4.3 逐句语义对照

原消息的每一个信息单元，都要在输出中找到含义相同的对应内容。至少逐项检查：

- 谁在做什么，作用于什么对象；
- 这是请求、承诺、接受、拒绝、问题、回答、报告还是普通陈述；
- 肯定、否定、条件、不确定性和强制程度；
- 需求及其包含和排除的范围；
- 决定及其力度；
- 当前执行状态；
- 前提条件、因果关系和时间顺序；
- 环境、生命周期、自动化方式、访问规则和技术选择；
- 原文刻意保留的歧义或开放问题；
- 列表的项目数、顺序和编号。

完成“原文到输出”的检查后，还要反向检查输出的每一个信息单元，确认它在原文中有依据，
从而发现编造内容。

### 4.4 业务值

- 识别每个数字、金额、比例、日期、期限、版本、文件名和标识分别代表什么；
- 允许具体值变化，但参数角色、单位、对象和约束不能变化；
- 同一消息中的相同数字可能属于不同参数，必须按位置分别判断；
- 列表编号、`ERC-721`、`AES-256` 等技术标识中的数字不是可随意改写的业务值；
- 如果原文明确说明总额、单价、数量之间的关系，输出的新值必须继续满足该关系；
- 如果某值在后续消息被修改、确认或删除，输出也必须保留同样的变化轨迹。

### 4.5 表达质量

- 输出应像真实聊天，不应出现明显机器拼接、重复句、无意义附加语或突兀说明；
- 不应出现乱码、`�`、截断单词、异常标点或破坏后的 Markdown/列表；
- 保持原消息所用语言和大致正式程度，不能无故换语言；
- 短回复应仍然简短，不能凭空加入承诺、原因或下一步；
- 长消息应有明显的自然改写，而不是只替换几个同义词；
- 不得为了流畅而删掉重复但有意义的需求、决定或状态。

一到两个词、且不含 PII、凭据或业务参数的短消息允许原样保留。不要仅因这类消息没有改写
就报告错误。

## 5. 完成逐条审核后的项目级检查

逐条检查结束后，还必须从整个项目的上下文再检查一次：

1. 同一个人、项目、组织、地点、账号或私有资源在不同消息中是否使用一致的虚构身份；
2. 原文中的不同实体是否被错误合并成同一个替换值；
3. 同一实体的全称、简称和别名是否保持合理对应；
4. 业务参数的引入、修改、确认和删除历史是否与原项目一致；
5. 项目级金额或数量关系是否在所有相关消息中一致；
6. 公共工具、技术、标准、文件格式和环境名是否在某些消息中被误改或丢失；
7. 同一私有值是否只在部分消息中被替换，另一些消息仍有残留；
8. 合成值是否与其他实体碰撞，导致两个不同对象看起来变成同一个对象；
9. 消息顺序和对话逻辑是否连贯，后文引用能否正确指向前文；
10. 是否存在单条看似正确、放回项目上下文后却改变事实的改写。

## 6. 不应使用的审核方法

- 不要只搜索原始字符串。漏抽取、别名、拆分写法和语义错误无法靠精确匹配发现；
- 不要把所有数值变化都判为错误，业务参数本来就允许合成；
- 不要把公共公司或技术名称当作 PII；
- 不要因为输出读起来更顺就默认正确；必须逐句核对事实；
- 不要因为 Phase 6、manifest 或流水线状态显示通过就跳过人工语义审核；
- 不要只看已由 Agent 修复过的消息；所有消息都要审核；
- 不要用“意思差不多”放过状态、否定、条件、范围或因果变化；
- 不要为满足个人写作偏好而报告纯审美差异。

## 7. 问题分类与严重程度

每个发现只选择一个最主要的 `code`：

| code | 含义 |
|---|---|
| `STRUCTURE_OR_COVERAGE_ERROR` | 消息缺失、重复、错位或字段结构错误 |
| `PII_RESIDUAL` | 原始 PII、别名或私有资源仍然存在 |
| `SECRET_OR_TOKEN_ERROR` | 真实凭据、内部标记或不安全假凭据问题 |
| `NON_PII_WRONGLY_CHANGED` | 公共名称、技术术语或普通词被误当成 PII |
| `ENTITY_MAPPING_INCONSISTENT` | 同一实体映射不一致，或不同实体发生碰撞 |
| `BUSINESS_VALUE_ERROR` | 业务值的角色、单位、位置、历史或关系错误 |
| `INTENT_OR_POLARITY_CHANGED` | 言语行为、否定、条件、不确定性或强制程度改变 |
| `DECISION_OR_STATUS_CHANGED` | 决定、歧义或执行状态改变 |
| `FACT_MISSING` | 原有项目事实、需求或限制丢失 |
| `FACT_INVENTED` | 输出增加原文没有的事实 |
| `RELATION_CHANGED` | 主体/对象、因果、时间、触发、访问或机制关系改变 |
| `PUBLIC_REQUIREMENT_CHANGED` | 公共工具、协议、标准或需求术语改变 |
| `LIST_OR_FORMAT_DAMAGED` | 列表、Markdown、语言或文本格式损坏 |
| `UNNATURAL_REWRITE` | 文本明显不自然、重复、乱码或机械拼接 |
| `REWRITE_TOO_WEAK` | 应改写的消息只做了表面同义词替换 |

严重程度：

- `BLOCKER`：真实 PII/凭据泄露，消息缺失、重复、错位，或输出无法追溯到当前源文件；
- `HIGH`：需求、决定、否定、状态、条件、公共技术、业务值关系等项目事实发生实质变化；
- `MEDIUM`：实体映射不一致、局部信息损坏、明显不自然或格式受损，但尚未证明核心事实改变；
- `LOW`：不影响隐私和事实的小型表达质量问题。

项目结论：

- `CLEAN`：没有发现问题；
- `PASS_WITH_MINOR_FINDINGS`：只有 `LOW`，可以发布但应留下记录；
- `NEEDS_REPAIR`：存在 `MEDIUM` 或 `HIGH`；
- `UNSAFE`：存在 `BLOCKER`，必须优先修复并重新审计。

## 8. 审核报告要求

Agent 不得在报告、终端回复、提交说明或日志中复制真实姓名、邮箱、链接、账号、凭据或其他
原始 PII。证据使用序号、字段、跨度和指纹定位；需要修复时，后续 Agent 再从本地源文件读取。

建议每个项目输出一份 JSON 报告：

```text
outputs/pii_postrelease_reviews/<项目ID>/audit_report.json
```

```json
{
  "schema_version": "pii-postrelease-agent-audit-v1",
  "project_id": "<项目ID>",
  "source_sha256": "<manifest 或重新计算的源文件指纹>",
  "output_sha256": "<重新计算的发布文件指纹>",
  "messages_total": 0,
  "messages_reviewed": 0,
  "project_status": "CLEAN",
  "findings": [
    {
      "finding_id": "<项目ID>:0001",
      "ordinal": 1,
      "severity": "HIGH",
      "code": "FACT_MISSING",
      "description": "输出遗漏了原消息中的访问条件；未在报告中复述敏感值。",
      "source_span": {"start": 0, "end": 12},
      "output_span": null,
      "confidence": "HIGH",
      "recommended_action": "恢复访问条件，同时保持现有合成身份不变。"
    }
  ],
  "project_level_checks": {
    "entity_consistency": "PASS",
    "slot_history": "PASS",
    "public_requirements": "PASS",
    "conversation_coherence": "PASS"
  }
}
```

要求：

- `messages_reviewed` 必须等于 `messages_total`，否则不得给出项目通过结论；
- `ordinal` 使用 1-based 数组位置；项目级问题可填 `null` 并列出相关 ordinals；
- `description` 说明“哪类事实变了”，不能复述真实 PII；
- 同一个根因不要为一条消息重复生成多个同义 finding；
- 无法确定时记录 finding，并把 `confidence` 设为 `LOW`，不要自行猜测；
- 报告必须绑定源文件和输出文件指纹。文件变化后，旧报告自动失效；
- 审核阶段不得直接改写发布文件。确认问题后，另开修复任务，修复后重新审核受影响消息及其
  项目级关系。

## 9. 单个项目的完成条件

只有同时满足以下条件，才算完成该项目审核：

- 原文件、发布文件和 manifest 已读取；
- 消息数量和字段结构已检查；
- 所有 ordinal 已逐条完成隐私、语义、业务值和表达质量检查；
- 已完成项目级一致性检查；
- 所有发现均已记录且未包含原始 PII；
- 报告中的两个文件指纹与当前文件一致；
- `messages_reviewed == messages_total`；
- 已给出 `CLEAN`、`PASS_WITH_MINOR_FINDINGS`、`NEEDS_REPAIR` 或 `UNSAFE` 之一。

## 10. 可直接交给 Agent 的指令

```text
请先完整阅读 Code/insturctions/PII_agent_audit_requirements.md，并严格按该文档审核项目 <项目ID>。

原文件：Datasets/project/<项目ID>/chat_messages.json
发布文件：Datasets/PII_clean_project/<项目ID>/chat_messages.json
manifest：Datasets/PII_clean_project/_manifests/<项目ID>.json

要求：
1. 按 1-based ordinal 对齐并审核全部消息，不抽样；
2. 同时检查 PII/凭据残留、误删的公共或技术内容、语义变化、业务值关系、跨消息一致性和表达质量；
3. 业务参数允许换值，但参数含义、单位、对象、条件、历史和关系必须保持；
4. 本轮只审核，不修改任何源文件、发布文件、manifest、流水线代码或校验器；
5. 报告中不要复制原始 PII，只用 ordinal、span、指纹和不含敏感值的描述定位；
6. 只有 messages_reviewed 等于 messages_total 后才能给项目结论；
7. 按文档第 8 节的结构写审核报告，并列出所有发现，包括 LOW 级小问题。
```
