# Agent Benchmark 数据分析报告

> 基础数据体检 + 初步指标分析
>
> 数据说明：该 Excel 不是单纯一张表，而是一个 agent benchmark/evaluation 数据库，核心在于：
> **Upwork 类任务 → 三个 agent 尝试完成 → evaluator 按多轮 turn 进行评价 → 失败的进入下一轮修改/重评。**

---

## 1. 数据整体结构

工作簿里主要有这些 sheet：

| Sheet                               | 主要内容                                    | 有效记录数 |
| ----------------------------------- | --------------------------------------- | --------: |
| `jobs`                              | 原始任务信息：标题、描述、类别、预算、附件、验收标准       | 145 个 job |
| `agent_traces`                      | agent 的 turn 0 提交内容和评价 JSON             | 312 条     |
| `evals_turn0`                       | 第 0 轮评价结果                               | 312 条     |
| `evals_turn1`                       | 第 1 轮评价结果                               | 186 条     |
| `evals_turn2`                       | 第 2 轮评价结果                               | 111 条     |
| `job_status`                        | 每个 job-agent-evaluator-thread 的状态流转记录   | 2142 条    |
| `assignments` / `turn1_assignments` | evaluator 分配情况                          | 145 个 job ID |
| `M5_submission_fails`               | 提交流程/Drive 文件等失败记录                      | 66 条      |
| `slack_evals`                       | Slack/Drive 侧 eval 文件状态                 | 70 条      |
| `Stats`                             | 汇总统计页，但部分公式显示 `#NAME?`                  |            |

一个重要结构是：`evals_turn0` 有 **312 条 = 104 个 job × 3 个 agent**。也就是说，虽然 `jobs` 里有 145 个任务定义，但当前真正进入完整 agent 评测链路的是 **104 个 job**，还有 **41 个 job 没有出现在 eval/traces 主评测数据里**。

## 4. 三轮评价结果：turn0 → turn1 → turn2

### 每轮单独看

| 轮次     | 评价记录数 | Pass | Fail | 当轮 Pass Rate | 平均 total_score |
| ------ | ----: | ---: | ---: | -----------: | -------------: |
| Turn 0 | 312   | 126  | 186  | 40.38%       | 0.7065         |
| Turn 1 | 186   | 75   | 111  | 40.32%       | 0.7147         |
| Turn 2 | 111   | 48   | 63   | 43.24%       | 0.7353         |

这里要注意：**Turn 1 的 186 条基本对应 Turn 0 失败的 186 条；Turn 2 的 111 条基本对应 Turn 1 失败的 111 条。**
所以这个流程不是每轮都重新评全部 312 个 attempt，而是：

> Turn 0 全部评估 → 失败的进入 Turn 1 → 仍失败的进入 Turn 2。

因此，当轮 pass rate 不能直接理解为整个系统成功率，而应该理解为“上一轮失败样本在这一轮被修复成功的比例”。

---

## 5. 累计成功率更有意义

如果把三轮累计起来看：

| 指标            | 数值        |
| ------------- | ---------: |
| 初始 attempt 总数 | 312        |
| Turn 0 已通过    | 126        |
| Turn 1 新增通过   | 75         |
| Turn 2 新增通过   | 48         |
| 三轮累计通过        | 249        |
| 三轮累计成功率       | **79.81%** |
| 仍未通过 / 未完成    | 63         |

这个结果说明：
**agent 初始一次完成率只有约 40%，但经过多轮反馈和修改后，累计成功率提升到约 80%。**

这是这个数据里非常关键的结论。

## 7. 从 job 角度看，三 agent 的最终通过情况

104 个进入评测的 job，每个 job 有 3 个 agent attempt。最终按“这个 job 有几个 agent 最终通过”统计：

| 每个 job 最终通过的 agent 数 | job 数 |
| -------------------- | ----: |
| 3 个 agent 都通过        | 66    |
| 2 个 agent 通过         | 22    |
| 1 个 agent 通过         | 7     |
| 0 个 agent 通过         | 9     |

也就是说，多数任务最终至少有 2 个 agent 可以完成；但有 **9 个 job 是三个 agent 都没有最终通过**，这些可能是高难度任务、需求不清晰任务、或验收标准很苛刻的任务，值得单独拉出来做 case study。

## 8. 按任务类型看成功率

按最终累计结果粗看：

| 子类型                    | Attempt 数 | 最终成功率 | 初始平均分 |
| ---------------------- | --------: | ----: | ----: |
| Full Stack Development | 105       | 84.8% | 0.707 |
| Back-End Development   | 54        | 81.5% | 0.745 |
| Front-End Development  | 141       | 74.5% | 0.683 |
| Prototyping            | 6         | 83.3% | 0.738 |

这里比较有意思的是：**Front-End Development 数量最多，但最终成功率相对更低**。这可能说明前端任务虽然看起来简单，但验收往往涉及 UI 细节、交互还原、响应式布局、视觉一致性等，容易因为细节不满足而 fail。

## 9. 数据质量问题 / 注意点

我初步发现几个需要注意的地方：

1. `Stats` 汇总页里有不少公式显示 `#NAME?`，所以不建议直接完全依赖 Stats 页，最好基于原始 eval 表重新算。

2. `jobs` 有 145 个任务，但 `evals_turn0/agent_traces` 只有 104 个 job，也就是当前完整评测覆盖率不是 100%。

3. `evals_turn0` 里有一条记录的 `turn` 字段看起来写成了 2，但它在 `evals_turn0` sheet 里。这个是一个小的数据一致性问题，后续精确分析时需要清洗。

4. `completed_at` 在 `evals_turn0/1/2` 中基本都是空的，因此暂时不能做严格的时间序列分析，比如“每轮耗时”“从提交到评价的延迟”等。

5. `assignments` 里虽然有 145 个 job ID，但有一部分没有 evaluator name；按有 evaluator 的记录看，大约 107 个 job 被分配给 evaluator。

---

## 10. 初步结论

这个数据的核心价值在于分析 **agent 在真实开发任务上的多轮修复能力**。单轮来看，三个 agent 的初始通过率并不高，整体只有约 **40.4%**；但经过 turn1、turn2 的反馈修复后，累计成功率提升到 **79.8%**。这说明多轮反馈机制对 agent 完成任务非常关键。

从 agent 对比看，`anthropic` 和 `openai` 表现接近，`anthropic` 略高；`google` 在初始通过率、累计通过率和平均评分上都偏低。
从任务类型看，前端任务数量最多，但最终成功率低于全栈和后端任务，后续可以重点分析前端失败是否集中在 UI 还原、交互行为、响应式布局或验收标准细节上。

下一步可以继续做三类深入分析：**agent 对比分析、失败原因/criteria 分析、turn0→turn1→turn2 的修复路径分析**。
