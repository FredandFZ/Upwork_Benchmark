# PII 清洗流程详解

## 1. 这套流程要解决什么问题

PII 清洗的目标，是把聊天记录中的真实身份信息、联系方式、私有链接、账号信息和敏感凭据，改成安全、自然的虚构内容，同时保留对话原本表达的需求、决定和执行结果。

例如，清洗后可以更换人名、邮箱、项目名和奖金数值，但不能把“不要上线”改成“可以上线”，也不能把消息中的金额关系、时间先后或任务状态改错。

程序只改写 `chat_messages.json`：

- `message` 会被清洗和改写；
- `sender_id` 与 `created_ts` 会从最终结果中删除；
- 其他字段保持不变；
- 项目目录中的其他文件会原样复制，不属于这套流程的清洗范围。

## 2. 整体流程

```text
原始聊天记录
   ↓
Phase 0：找出凭据和身份信息
   ↓
Phase 1：理解每条消息以及整个项目的业务含义
   ↓
Phase 2：制定全项目统一的替换方案
   ↓
Phase 3：按照方案改写消息
   ↓
Phase 4：独立检查改写是否正确
   ├─ 通过 ─────────────────────────┐
   └─ 失败 → Phase 5：LLM 自动修复  │
                  ├─ 修复成功 ──────┤
                  └─ 仍然失败 → Agent
                                      ↓
Phase 6：本地生成假凭据并做最终安全审计
   ↓
发布清洗后的 chat_messages.json
```

这里最重要的顺序是：**先理解，再计划，再改写，再检查。Agent 的文本修复放在 Phase 5 之后，作为自动修复失败后的最后补救手段。**

本文中的“LLM”和“Agent”不是一回事：LLM API 是程序在各阶段自动发出的模型请求；Agent 是自动流程无法完成任务后，读取专门的修复任务并处理少量失败消息的独立执行者。

## 3. Phase 0：找出需要保护的信息

### Phase 0A：先屏蔽密码和密钥

这一阶段由本地程序完成，不调用 LLM API。

它负责寻找真正具有访问权限的敏感信息，例如：

- API Key、Access Token 和 Bearer Token；
- 密码和邮件服务器凭据；
- 私钥、助记词和 Webhook Secret。

程序先把这些内容替换成内部临时标记。后面的 LLM 和 Agent 只能看到临时标记，看不到真实凭据。

这一阶段只处理“可以用来登录或获得权限”的秘密。人名、邮箱、用户名和账号编号属于身份信息，交给 Phase 0B 处理。

产出：一份已经隐藏真实凭据的安全文本，供后续阶段使用。

### Phase 0B：识别身份信息

这一阶段调用 LLM API，但只负责识别和分类，不修改消息。

它会找出：

- 人名、邮箱、电话和社交账号；
- 私有公司、项目名、域名、仓库和链接；
- 地址、钱包地址、账号标识和能够识别个人的经历描述。

公共工具和技术名称通常保留，例如 GitHub、Stripe、AWS 和 OAuth。普通英文单词如果不能单独识别某个项目或个人，也不应被当成项目名。例如，完整的 `Project Rebuild` 可以是项目名，但普通动词 `rebuild` 本身不是可靠的项目标识。

产出：每条消息中身份信息的准确位置，以及哪些内容需要替换、哪些公共名称必须保留。

## 4. Phase 1：理解消息在说什么

### Phase 1A：逐条理解消息

这一阶段调用 LLM API，逐条分析消息的业务含义。

它主要回答：

- 这句话是在提出要求、作出决定、询问问题，还是报告执行结果？
- 这句话是肯定、否定，还是带有不确定性？
- 金额、数量、日期、百分比等数值分别代表什么业务参数？
- 一个业务值在消息中的准确位置在哪里？

例如，同一条消息里可能同时出现“5 名获奖者”“10 月 1 日”和“20%”。Phase 1A 不会把所有数字混在一起，而是分别说明每个数字的含义和位置。

这也是裸数字问题的关键修复：一个单独的 `5` 不再表示“把整条消息里所有 5 都替换掉”，而只表示某个明确位置上的业务值。如果无法安全确定位置，它只作为语义信息记录，不执行盲目字符串替换。

产出：每条消息的含义说明，以及按出现位置记录的业务值。

### Phase 1B：把整个项目的含义合并起来

这一阶段调用 LLM API，把 Phase 1A 的逐条结果按时间顺序汇总。

它主要处理跨消息关系：

- 两条消息里的“获奖人数”是否是同一个参数；
- 某个数值后来是否被修改；
- 当前最终生效的值是什么；
- 数量、单价和总额之间是否存在计算关系；
- 项目历史中是否存在互相矛盾的说法。

它不会为了让数据看起来整齐而编造一致性。如果原始对话本身存在冲突，流程会如实记录这个冲突。

产出：一份项目级业务说明，记录参数名称、变化历史和相互关系。

## 5. Phase 2：制定统一替换方案

这一阶段调用 LLM API，并由本地程序检查和汇总结果。

Phase 2 不改写完整消息，而是先制定一份全项目共用的替换方案：

- 每个人名、邮箱、项目名和私有链接换成什么虚构内容；
- 每个业务参数换成什么新值；
- 同一个实体在不同消息里必须使用同一个新名称；
- 相互关联的值必须继续满足原来的关系；
- 公共工具和技术名称保持不变。

业务值的替换按出现位置保存，而不是使用全局字符串替换。因此，消息中的日期、百分比、列表编号和其他相同数字不会被误改。

产出：全项目唯一的替换方案。后面的改写和检查都以这份方案为准。

## 6. Phase 3：按照方案改写消息

这一阶段调用 LLM API，真正生成新的消息文本。

Phase 3 分别处理短消息和长消息，但目标相同：

- 应替换的身份信息必须换成 Phase 2 指定的虚构值；
- 应调整的业务值必须使用其对应位置上的计划值；
- 原来的需求、决定、否定关系和执行状态必须保留；
- 长消息需要改变表达方式和组织结构，不能只做机械替换；
- 公共名称和必须保留的内容不能被改坏。

程序会先做一轮本地检查。明显违反替换方案、遗留真实身份信息或几乎照抄原文的结果，不会进入最终数据。

产出：候选改写文本。

## 7. Phase 4：独立检查改写结果

这一阶段使用独立的 LLM 检查 Phase 3 的候选文本。

它会重新阅读原消息和改写结果，判断：

- 原意是否保持；
- 肯定和否定是否被翻转；
- 需求、决定和执行状态是否改变；
- 身份信息和业务值是否按计划替换；
- 相关金额、数量和日期关系是否仍然成立；
- 改写是否自然，是否真的不同于原文。

Phase 4 只负责判断和指出问题，不直接修改文本。即使 LLM 判断通过，本地程序仍会执行可以明确判断的安全检查。

产出：通过结果，或者一份说明具体问题的检查报告。

## 8. Phase 5：自动定向修复

Phase 5 仍然是 LLM API 阶段，**不是 Agent 阶段**。

它只处理 Phase 4 没有通过的消息，并把具体错误告诉 LLM。例如：

- 某个真实人名还没有被替换；
- 计划中的金额没有正确应用；
- 否定含义被改反；
- 改写与原文过于接近。

LLM 根据这些明确的问题进行定向修复。每次修复后，结果都要重新经过检查。自动修复次数有限，避免程序围绕同一个错误无限重试。

产出有两种：

- 修复成功：进入 Phase 6；
- 仍然失败：隔离该消息，等待 Agent 处理，不发布不完整的数据。

## 9. Agent 在什么时候介入

### 9.1 正常原则：在 Phase 5 之后介入

Agent 不参与正常的批量识别、规划和首次改写。它的主要使用时机是：

1. Phase 3 已尝试生成文本；
2. Phase 4 已指出问题；
3. Phase 5 已尝试自动修复；
4. 自动流程仍然不能得到合格文本；
5. 程序生成 Agent 任务包并暂停发布；
6. Agent 根据任务包修改这些失败消息；
7. Agent 的结果通过本地检查后，再进入 Phase 6。

因此，**Agent 是自动流程之后的补救层，而不是 Phase 3 的默认改写工具，也不是 Phase 5 本身。**

有一种细节需要说明：如果一条消息在 Phase 3 的本地硬检查中已经失败，它无法继续进入 Phase 4 和 Phase 5。程序仍会等整个 Phase 3–5 自动阶段结束后，再统一把这条消息交给 Agent。也就是说，Agent 的介入时间仍在自动阶段之后，但并非每一条 Agent 任务都实际经历过 Phase 5。

### 9.2 Agent 实际修改什么

程序会在 `outputs/pii_runs/<project_id>/agent_tasks/` 中生成任务。任务会告诉 Agent：

- 原消息在表达什么；
- 上一次候选文本是什么；
- 哪些检查没有通过；
- 哪些虚构名称和业务值必须使用；
- 哪些公共名称和内部凭据标记必须保留。

Agent 只提交失败消息的新文本，不直接修改原始数据，也不直接发布结果。提交结果写入 `agent_repairs/repairs.json`，随后由 `pii_finalize.py` 检查和合并。

Agent 不能自行生成 `FAKE_*` 凭据，也不能删除内部凭据标记；这些工作统一留给 Phase 6，避免不同消息使用不一致的假凭据。

### 9.3 哪些问题不应交给 Agent

- API 断线或超时：重新运行原命令，从 checkpoint 继续；
- Phase 2 的整体方案无法建立：重新运行或修复 Phase 2；
- 程序结构、输入格式或安全审计本身出错：修复代码或源数据。

Agent 擅长修复具体文本，不适合解决网络故障或重新制定整份项目方案。

少数 Phase 0B/1A 的内容识别失败也可以生成“补充标注”任务。此时 Agent 只补充缺失的识别结果，不修改最终消息；补充结果必须由下一次 `pii_clean.py` 运行重新纳入 Phase 2。这个例外不改变“消息文本修复在 Phase 5 之后进行”的原则。

## 10. Phase 6：生成最终文本并做安全审计

Phase 6 完全由本地程序执行，**不调用 LLM API**。

### Phase 6A：生成确定无效的假凭据

程序把 Phase 0A 留下的内部凭据标记，统一变成明显无效且可重复生成的 `FAKE_*` 字符串。

这样既不会泄露真实密钥，也不会让 LLM 或 Agent 猜测凭据格式。

### Phase 6B：最终安全审计

程序对整个项目做最后检查，重点确认：

- 原始人名、邮箱、电话、项目标识和私有链接没有残留；
- 原始凭据和内部临时标记没有残留；
- 每个实体在全项目中使用一致的虚构值；
- 业务值按正确的消息位置应用；
- 公共名称和列表编号没有被破坏；
- 每条需要修改的消息确实已经修改；
- 所有消息都经过了必要的改写或检查；
- 没有任何尚未解决的消息。

6B 是本地规则检查，不会再次请 LLM 判断语义。若使用了 Agent，`pii_finalize.py` 会先严格检查 Agent 提交，再运行 6A 和 6B。

只有 6B 零错误时，程序才会发布最终的 `chat_messages.json`。只要还有一条未解决消息，就不会生成或覆盖最终结果。

## 11. 出现报错时，流程会怎么处理

一条消息或一个批次报错，通常不代表整个项目立即失败。程序会先尝试自动恢复，并继续处理同阶段的其他消息。只有问题经过自动恢复后仍然存在，程序才会在当前阶段组结束时停止该项目。

```text
出现错误
   ↓
自动重试，或把失败批次逐级拆小
   ↓
问题解决 ──→ 继续后面的阶段
   ↓ 没有解决
继续检查当前阶段的其他消息
   ↓
到达安全的阶段边界后停止，不发布不完整结果
```

各阶段的具体行为如下：

- **Phase 0B / 1A**：批次失败后，程序会把批次逐级二分，只继续拆分没有通过的一半，直到找到具体失败消息；其他消息继续运行。如果最后仍有消息失败，流程会在信息抽取阶段结束后停止。
- **Phase 1A 的位置校正**：模型负责判断一个业务值是什么意思，本地程序负责精确计算它在原消息中的位置。如果模型给出的 `start/end` 有偏差，但 `source_literal` 能在消息中唯一定位，本地会自动纠正；找不到或存在无法判断的多处匹配时才报错。
- **Phase 1B / 2**：它们产生的是一份全项目结果，不能只跳过其中一条消息。自动重试后仍然失败，就停止当前项目。
- **Phase 3 / 4 / 5**：一条消息失败不会影响其他消息继续处理。Phase 4 检查失败时，先由 Phase 5 自动修复；自动修复仍失败，才在这一组阶段结束后生成 Agent 任务。
- **Phase 6**：程序会尽量一次列出全部审计问题，但只要存在一项必须解决的错误，就不会发布最终数据。

例如，终端出现：

```text
[42204309] PHASE_0B_PII_DISCOVERY shard_0001 failed validation; bisecting 40 item(s)
```

它的意思不是“整个项目失败”，而是：这个包含 40 条消息的批量结果没有通过检查，程序正在将它拆成两个 20 条批次。通过的一半会整体保存；只有失败的一半继续拆成 10 条、5 条，必要时才缩小到单条消息。

常见终端提示可以这样理解：

| 终端提示 | 含义 |
|---|---|
| `failed validation; bisecting ...` | 批量结果未通过检查，正在逐级二分以定位失败消息；流程仍在运行 |
| `transport exhausted; bisecting ...` | 大批次连接或响应失败，正在拆成更小批次；流程仍在运行 |
| `UNRESOLVED ... continuing` | 某条消息暂时没有解决，但程序会继续检查当前阶段的其他消息 |
| `BLOCKED_RETRYABLE` | 当前项目已停止，通常修复网络问题后重新运行同一命令即可 |
| `REPLAN_REQUIRED` | 当前项目已停止，需要重新运行发生问题的规划阶段 |
| `AWAITING_AGENT_REPAIR` | 自动文本修复已经结束，当前项目正在等待 Agent 处理 |
| `FATAL` 或 `FAILED` | 当前项目因严重错误停止 |
| `DONE` | 所有阶段完成，最终结果已经通过检查并发布 |

如果同时处理多个项目，一个项目停止通常不会让其他项目一起停止。无论哪种情况，流程都不会把未解决的消息偷偷换回原文并发布。

## 12. 三条最重要的理解

1. **Phase 0–2 负责找全信息并制定统一方案，Phase 3 才真正改写文本。**
2. **Phase 4 负责发现问题，Phase 5 使用 LLM 自动修复；Agent 在自动修复仍失败后介入。**
3. **Phase 6 不使用 LLM，它只负责本地渲染和最终安全审计；审计不通过就不发布。**

## 13. 断点续跑

每个阶段和每条消息都有 checkpoint。运行中断后，再次执行同一条命令会复用已经通过且仍然有效的结果。

只有上游内容或规则发生变化时，依赖它的下游结果才需要重跑。例如，Phase 2 的替换方案发生变化后，Phase 3 的改写不能继续沿用旧方案，因此需要重新生成；但与变化无关且仍然有效的逐消息结果可以继续复用。

`--force-phase` 会主动删除指定阶段及其下游 checkpoint，只应在确实需要重算时使用。普通网络中断不需要添加这个参数。

运行命令和 Agent 提交流程见 [`README_PII_Clean.md`](../Code/insturctions/README_PII_Clean.md)。
